## 4. Separate `hooks.Bus` inventory (requirement 5.7)

`hooks.Bus` (`internal/core/hooks/bus.go:21-27`) is **not** a typed plane and is
not assumed covered by the plane manifest. It owns four sorted chains
(`submit`, `requestParts`, `responseParts`, `tools`) built by
`MaterializeSorted` from `HookConfig` (order, id, registration index).
`HookConfig` is the generated projection of exactly four hook-target planes
(`ProjectHookConfig`, `plane_generated.go:3009`); the ratchet asserts the
annotated set stays exactly
`submit_hooks`/`request_part_hooks`/`response_part_hooks`/`tool_reactors` and
that an occupied chain on each projects 1:1 into the bus
(`HookChainLengths == (1,1,1,1)` in test).

Chain classification from the SDK shapes
(`pkg/lipsdk/hooks/submit.go:56-60`, `parts.go:21-35`, `toolreactor.go:44-47`):

- `submit` — `Handle(ctx, *Call, *SubmitMeta)`: inspects/mutates the canonical
  request pre-route, can reject. Canonical-required when occupied.
- `requestParts` — `HandleRequestParts(ctx, *Call, PartMeta)`: mutates request
  parts (reference: `refparts` appends a suffix to user text). Canonical-required
  when occupied.
- `tools` — `HandleToolEvent(ctx, ToolEvent, ToolMeta)`: observes/rewrites tool
  lifecycle events on the request path. Canonical-required when occupied unless
  given an explicit typed wire contract (Task 3.3).
- `responseParts` — `HandleEvent(ctx, *Event, PartMeta)`: response events only.
  May remain active when proven response-only (req 13.6).
