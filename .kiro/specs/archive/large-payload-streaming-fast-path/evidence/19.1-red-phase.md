## 1. Mutation A: Gauge Sequence Ordering (RED Phase)

Finding 1 identified that `spool.go` observer callbacks fire outside `l.mu`. Under concurrency, a stale snapshot could overwrite a newer gauge value (e.g. `Reserve` snapshot applied after `Release`).
To verify the ordering requirement, a deterministic test was added in `internal/infra/metrics/large_payload_prom_test.go`:
- `TestLargePayloadProm_ActiveSpoolSequenceOrdering` simulates an out-of-order notification where older sequence `seq=1, bytes=1000` arrives after newer sequence `seq=2, bytes=500`.
Without sequence filtering in `largePayloadPromSink.OnActiveSpoolBytes`, the stale snapshot overwrote the gauge to 1000 instead of keeping 500.

Command executed:
```pwsh
go test -v -count=1 -run TestLargePayloadProm_ActiveSpoolSequenceOrdering ./internal/infra/metrics/
```

Verbatim failing output (Exit code 1):
```text
=== RUN   TestLargePayloadProm_ActiveSpoolSequenceOrdering
=== PAUSE TestLargePayloadProm_ActiveSpoolSequenceOrdering
=== CONT  TestLargePayloadProm_ActiveSpoolSequenceOrdering
    large_payload_prom_test.go:192: expected 500 after stale update, got 1000
--- FAIL: TestLargePayloadProm_ActiveSpoolSequenceOrdering (0.00s)
FAIL
FAIL	github.com/matdev83/go-llm-interactive-proxy/internal/infra/metrics	0.035s
FAIL
```

Remediation applied:
- Added a monotonic `seq uint64` counter to `SpoolLedger`, incremented inside `l.mu` on every state mutation (`Reserve`, `ReserveMore`, `ShrinkTo`, `Release`).
- Passed `(seq, inflight)` to `SpoolObserver.OnActiveSpoolBytes(seq uint64, bytes int64)`.
- Updated `largePayloadPromSink` with a mutex and `lastSeq uint64` filter: incoming notifications with `seq < lastSeq` are discarded.
- Added both deterministic unit tests and 40-goroutine concurrent ordering tests proving `final gauge == ledger.InflightBytes() == 0`.

## 4. Review Remediation Documentation (Finding 3)

1. **Decline-reason coarseness**:
   - `proofErr`: all profile proof compilation failures map to `proof_uncertain` because at the profile boundary, any failure to validate protocol semantic facts or schema constraints indicates wire equivalence cannot be guaranteed without full canonical parsing. This is intentional: the pipeline should not branch into speculative provider-specific decline reasons when proof validation fails.
   - `assessErr`: cancellation/deadline expiry maps to `canceled`. Other assessor errors (unconfigured assessor, authority reject) map to `authority_blocker` because the assessor is the exclusive authority blocker for wire execution.
2. **Gating `gateStart = time.Now()` on disabled path**:
   - In `internal/plugins/frontends/frontendpipe/pipe.go`, `gateStart = time.Now()` is gated behind `if spec.LargePayload.Enabled`. When the fast path is disabled (production default), zero `time.Now()` calls are made during pre-capture gating, completely avoiding syscall overhead. Overhead quantification will be benchmarked in Task 19.4.
3. **Dead `"wire_execution"` allowlist entry removal**:
   - Removed `"wire_execution"` from `sanitizeDurationStage` in `internal/infra/metrics/large_payload_prom.go`. The stage emitted by `replayCandidate` is `"execution"`.
4. **Unwired-production status**:
   - `Bundle.LargePayloadDiagnostics()` and `SpoolLedger.SetObserver()` are implemented and tested, but currently have no production callers in HTTP server startup because the large-payload streaming fast-path feature is default-off. Full runtime startup wiring is deferred to the enablement task (Task 20 / 23).
