# Requirements Document

## Project Description (Input)
Add a Claude agent backend to AIProxer through the maintained upstream ACP adapter (`@agentclientprotocol/claude-agent-acp`, the "Zed variant"), which runs Anthropic's official Claude Agent SDK. Operators can then route requests to a local Claude agent. It authenticates with an explicitly selected source: an operator-supplied Anthropic API key, or the operator's Claude subscription through either an official long-lived subscription token or the host's existing Claude login. Source: GitHub issue #705 and its research comments, including the managed-policy blocker resolution of 2026-10-11.

- **Who has the problem:** single-user AIProxer operators who use Claude Code and want AIProxer clients to reach a Claude agent, often on their existing Claude Pro/Max plan rather than a separate API bill.
- **Current situation:** AIProxer offers Claude only as raw inference through the native `anthropic` backend (API key) and cloud connectors. Raw OAuth subscription bridges are unsupported by policy (`docs/backend-plugins/unsupported.md`). The repository already has an ACP stdio connector family (`cursorcliacp`, `agycliacp`, `geminicliacp`) on `connector-support/acp`. However, its generic defaults (empty-object permission replies, full environment inheritance, the hard-coded `reasoning_effort` option, CLI `--model` flags) are unsafe or incorrect for Claude.
- **What should change:** a new optional executable connector launches an operator-installed, version-checked Claude ACP adapter. It selects the authentication source explicitly and never implements OAuth login, credential extraction, or refresh itself. It answers tool permission requests safely, auto-discovers model identities and effort capabilities without hardcoded model names, honors canonical fully qualified selectors, and streams turns through the existing canonical path. The operator-facing instance name is `claude-acp`; model identity uses the existing `anthropic/` namespace, independently of backend selection.

## Introduction
This slice adds one optional local agent-runtime connector. It reuses the existing ACP subprocess runtime and the executable backend-plugin ABI. Core routing, B2BUA continuity, canonical contracts, and other ACP connectors' behaviour are unchanged.

## V1 Slice
- **Delivers**: an operator can configure a `claudeagentacp` backend instance and route a streamed multi-turn request to a local Claude agent. Authentication is an explicitly selected credential source: an API key (the default), an operator-provisioned subscription token from the official `claude setup-token` flow, or the host's existing Claude login. Tools are disabled by default; a certified foreground subset requires explicit operator opt-in.
- **First consumer**: any AIProxer frontend client routed with an explicit `claude-acp:anthropic/<canonical-model>` selector on a single-user loopback deployment, including existing selector query options for reasoning effort.
- **Safe degradation**: a missing adapter, an uncertified adapter/runtime profile, missing credentials, an expired login, an effective credential or provider that differs from the selected source, administrator-managed policy that the operator has not chosen to honour, and an unadvertised model or effort fail before a prompt; unrecognised agent requests receive explicit errors in every lifecycle phase. Nothing falls back to another credential source, model, or backend inside the connector.

## Boundary Context
- **In scope**: the new `claudeagentacp` connector module and its manifest, release metadata, configuration, adapter resolution and version check, credential-source environment and configuration roots, identity and administrator-policy gates, permission policy, model and effort session options, and diagnostics. Also small opt-in session and transport seams in `connector-support/acp` for retained model-dependent options, connector-owned session metadata and refusals outside active prompts. Plus an operator config example and a short operator doc section.
- **Out of scope**: implementing Claude OAuth, reading, copying, linking or refreshing Claude credential stores, reusing Claude Code client identity or headers, disabling, masking or overriding administrator-managed Claude policy (including by container or namespace masking of policy locations), redistributing the adapter, the Agent SDK, or the Claude CLI, installing npm packages, multi-user or shared-credential operation, changing the native `anthropic` backend, and changing other ACP connectors' behaviour.
- **Adjacent expectations**: the operator installs Node and a certified `claude-agent-acp` release. For subscription use the operator either runs the official `claude setup-token` and provisions the token as a connector secret, or has logged in with `claude auth login` on the host; in both cases the operator accepts their Claude plan's terms. The host enforces `local_only` and `agent_runtime` posture from the manifest.
- **Trust model**: administrator-managed Claude policy (system or device-management policy, policy helpers, and organisation-delivered server policy) is trusted out-of-band authority that the Claude runtime enforces by design above every other setting. The connector detects and discloses it, refuses it by default as an operator-consent decision, and never bypasses it; this is not a security boundary against a root or same-user attacker, who is outside the `local_only` threat model. Everything the operator's user account can write that the connector launches with (environment, configuration directory, user and project settings, MCP, plugins, tools) is connector-controlled.
- **Boundary ownership**: backend plugin (`connectors/claudeagentacp`) plus connector support (`connector-support/acp`, additive seams), and bounded generic config/runtimebundle/processhost/private resource identity/reload wiring for this first stock-host consumer's instance-scoped provisioning. Public Options, SDK, ABI and core provider neutrality remain unchanged.
- **Revalidation triggers**: backend-plugin ABI or manifest posture rules; `connector-support/acp` handshake, protocol, or server-request seams; the upstream adapter's authentication methods, configuration option IDs, or permission option kinds; Claude Code managed-policy locations, parent-settings semantics, credential precedence, or `auth status` output; Anthropic policy on third-party subscription use.

## Requirements

### Requirement 1: Optional local agent-runtime installation
**Objective:** As a single-user operator, I want to enable a Claude agent backend without changing the standard host, so that Claude agent support is optional and safely scoped.

#### Acceptance Criteria
1. When an operator configures a Claude Agent backend instance and the adapter executable is resolvable, the Claude Agent connector shall start the adapter on first use without installing, downloading, or updating any package.
2. If the adapter executable cannot be resolved or reports a version outside an explicitly certified adapter/runtime profile, then the Claude Agent connector shall reject the instance with a diagnostic that names the missing prerequisite and its remediation.
3. The Claude Agent connector shall declare itself an agent runtime that is restricted to local single-user deployments, so that a multi-user deployment rejects it before any agent process starts.
4. The Claude Agent connector shall use a backend kind distinct from the native Anthropic API backend and support the unique operator-facing instance name `claude-acp`, so that `claude-acp:anthropic/<canonical-model>` selects the agent runtime without changing the canonical model's provider identity or introducing a host dependency on Node for unused connector features.

### Requirement 2: Explicit credential source and policy authority
**Objective:** As an operator, I want to choose whether the Claude agent uses my API key or my Claude subscription, and to know which policy governs it, so that billing is predictable and AIProxer never implements, extracts, or bypasses Claude login or policy.

#### Acceptance Criteria
1. The Claude Agent connector shall support exactly three explicitly selected credential sources (API key as the default, an operator-provisioned subscription token, and the host's existing Claude login), shall never fall back from one source to another, and shall reject an instance whose selected source lacks its required secret.
2. While using the API key or the subscription token, the Claude Agent connector shall launch each agent process with a fresh connector-owned configuration and home root that is deleted when the process ends, so that no host Claude settings, cached policy, credentials, or session files are read or written.
3. While using the host's existing Claude login, the Claude Agent connector shall run the agent against the host's own Claude configuration directory without reading, copying, linking, or refreshing its credentials itself, and shall disclose that the instance runs with the same trust and policy as the operator's own Claude CLI.
4. The Claude Agent connector shall never initiate login, interpret tokens, or refresh credentials; it shall pass a provisioned secret only to its child process and shall never place a credential on a command line, in a log, or in diagnostics output.
5. Before each user prompt is admitted to the SDK query, the Claude Agent connector shall obtain a fresh, session-query-bound observation that the runtime's currently applied credential and provider match the selected source (an API key with the first-party provider, or a subscription login with the first-party provider and no API key), and shall reject unknown, stale, conflicting or mismatched evidence without admitting user input. Independent CLI probes and auth notifications alone shall not authorize a prompt.
6. If administrator-managed Claude policy applies or its absence cannot be established, then the Claude Agent connector shall by default refuse before runtime execution and name the known or potential policy source, shall start only when the operator selected the honour setting, shall re-check observable local and cached policy before each turn and replace the agent process when that fingerprint changes, shall never disable, mask, or override that policy, and shall record the credential source, runtime identity and policy disposition without secret values. Remote policy fetching and polling remain CLI-owned: fresh current-applied identity is not a remote-policy refresh or latest-revision certificate, and this limitation shall be disclosed.
7. If the agent reports that authentication is required, then the Claude Agent connector shall return a redacted authentication failure stating that the selected credential is missing or expired and naming the remediation command, without retrying after output.

### Requirement 3: Safe headless permissions and process isolation
**Objective:** As an operator, I want an HTTP-driven Claude agent to act only as I allow, so that a proxy request can never silently approve file edits or commands.

#### Acceptance Criteria
1. While the deny policy is active, the Claude Agent connector shall expose no executable agent tools and shall decline any permission request, including when local settings would normally auto-approve it.
2. Where the operator enabled the allow policy, the Claude Agent connector shall permit only a certified foreground tool set during an active turn, select a one-time allow option when offered, and never select persistent approval or bypass-permissions mode.
3. If a request arrives before or between turns, a permission request offers no safe matching option, or the agent sends an unrecognised request, then the Claude Agent connector shall answer with a refusal or error rather than an empty success.
4. When starting an agent, the Claude Agent connector shall use the session-discovered working directory when available, otherwise the configured default, and an explicit environment allowlist and connector-owned session settings that load no user or project settings, hooks, MCP servers, plugins, or permission rules, and that add a restrictive host policy limiting the provider to Anthropic and disabling hooks and bypass mode; where the certified runtime does not honour one of these controls, the connector shall not enable that runtime profile.
5. The Claude Agent connector shall start the agent with agent background/subagent facilities excluded and shall refuse detached execution inputs; cancellation and shutdown shall quiesce the owned process tree without claiming to undo external effects of approved foreground tools.

### Requirement 4: Exact model and effort selection
**Objective:** As a client developer, I want my requested Claude model and reasoning effort applied exactly, so that the agent never silently runs a different configuration.

#### Acceptance Criteria
1. When a request selects a canonical Claude model, the Claude Agent connector shall configure the agent session with its exact runtime-discovered native model identity, shall publish the same discovered canonical/native identities in model inventory, and shall derive selection from runtime discovery without hardcoded model names, family-specific mapping tables, or moving-alias substitution for a versioned request.
2. If the requested model is not in the connector's model inventory or is not advertised by the agent, then the Claude Agent connector shall reject the request before any output without substituting another model.
3. When a request specifies a reasoning effort through the existing selector query syntax or canonical request options, the Claude Agent connector shall configure the agent's effort option with that exact value when it is advertised for the selected model, using refreshed options after model selection.
4. If the requested reasoning effort value is not advertised by the agent, then the Claude Agent connector shall reject the request with an explicit capability error before any output, without retaining a previous turn's effort when the current request omits effort.
5. The shared ACP connector support shall keep the existing model and reasoning-effort behaviour of the Cursor, Gemini, and AGY connectors unchanged.

### Requirement 5: Streamed turn lifecycle
**Objective:** As a client, I want Claude agent turns to stream, cancel, and fail like other AIProxer backends, so that clients need no Claude-specific handling.

#### Acceptance Criteria
1. When the agent streams message text and thinking, the Claude Agent connector shall emit them in order as canonical text and reasoning deltas; while the client session, resolved workspace, selected native model, history and applied configuration remain compatible, subsequent turns shall reuse the same agent conversation and process, and requests for different projects shall not share project state or spawn a replacement process on every compatible turn.
2. When the client cancels a request, the Claude Agent connector shall cancel the agent turn and end the stream with exactly one terminal outcome.
3. If the agent process exits or fails before any output, then the Claude Agent connector shall return a pre-output failure eligible for the operator's configured failover, and if it fails after output the connector shall end the stream with an error and never retry.
4. When the proxy stops, the connector shuts down or reaps an idle agent, or a successfully published reconfiguration no longer uses an instance after its admitted work drains, the Claude Agent connector shall terminate the corresponding owned agent process and its child process tree while preserving unaffected instances; a rejected reconfiguration shall not terminate the active instance.
