## Primary Evidence (2026-10-11)
Upstream source snapshot: [claude-agent-acp 4e1fc1e8](https://github.com/agentclientprotocol/claude-agent-acp/tree/4e1fc1e8df2b9af3b1b2d6880ba90c5862283ba8). Its package.json declares adapter 0.89.1 and Agent SDK 0.3.293. Reviewed `src/acp-agent.ts`, `src/index.ts`, `src/settings.ts` and package metadata. These are observed source contracts, not proof that every installed distribution matches this snapshot.

- Adapter session metadata accepts `_meta.claudeCode.options`. Its query defaults load `settingSources: [user, project, local]`; it merges user options/environment, settings and MCP configuration. Environment filtering alone therefore cannot establish auth or permission isolation.
- `SettingsManager` separately resolves and watches user/project/local/managed settings. `settingSources: []` on query does not remove that adapter-side state. Mode/model changes and managed precedence must be exercised in certification.
- `allowDangerouslySkipPermissions: false` excludes bypass behavior; permissionMode is adapter-managed. Establish an explicit non-bypass mode instead of assuming SDK override fields work.
- Deny-by-default requires `tools: []`, because permission allow rules can avoid an ACP permission callback. Allow mode requires a limited certified foreground subset, not a blanket approval callback.
- `claudeCliPath` resolves the SDK's platform-specific bundled CLI dependency; inherited CLAUDE_CODE_EXECUTABLE overrides it. The connector excludes this override and never downloads dependencies.
- Adapter model selection rebuilds configOptions, including effort capabilities. After a model change, old session/new effort values are stale. A pooled turn with no requested effort must restore the negotiated default instead of inheriting a previous request's explicit effort.
- Upstream tracks non-subagent background tasks that can outlive turns. CLAUDE_CODE_DISABLE_BACKGROUND_TASKS is only defense in depth; no source-based guarantee that arbitrary approved commands produce no continuing external effects.
- `--hide-claude-auth` hides subscription authentication. Auth mode must also isolate effective SDK settings and provider/helper overrides. Operator-provisioned CLAUDE_CODE_OAUTH_TOKEN is opaque secret input; a claim that LIP never transmits any token would contradict that feature.

## Alternatives and Proportionality
Select a thin external connector on existing ACP runtime with private transport-scoped negotiated state and a narrow opt-in refusal policy. Reject a second ACP client, global session map, required canonical/ABI change, or generic effect/container framework. Two demonstrated shared gaps justify the additions; no estimated line count substitutes for reviewing their actual implementation. No provider SDK enters core.

## Lifecycle Validation (Cordis-derived discipline)
- Immutable credentials/profile belong to the configured instance; the existing per-instance pool cannot mix authentication modes.
- Pool remains sole owner of subprocess tree and transport. Session metadata belongs to that transport generation and disappears on reap/divergence/Close; per-turn BindSession only borrows it under the existing runtime claim.
- Transport policy is installed before reading the first byte, so initial/handshake/inter-turn requests cannot receive accidental success. No extra detached callback/task owner is introduced.
- Failed model/effort exchange invalidates the ambiguous runtime. Separate sessions cannot share negotiated state; replacement cannot inherit stale state.
- Cancel/shutdown quiesce owned processes. Foreground tool actions and billing are external effects, not rollback-capable resources. Post-output failure never retries.

## Design Review and Repairs
Critical findings in #910 were repaired across requirements/design/tasks:
1. Source-only environment scrub contradicted default settings/helper loading: require connector-owned SDK options, managed-policy fail-closed behavior and real profile certification.
2. Deferred out-of-turn routing contradicted the promised refusal policy: bring opt-in transport refusal into V1.
3. Claimed pooled option state had no storage seam across Handshake/BindSession: assign it to private transport state, with refreshed model-dependent options and reset semantics.
4. Background flag implied an unsupported no-work-after-response guarantee: exclude background/subagent facilities and state the limits of approved external effects.
5. Opaque token transport contradicted "never transmit login credentials": distinguish operator-provisioned secret transport from login/store extraction/refresh.
6. Minimum version could admit changed security behavior: certify exact runtime profiles instead.
7. Item 1's managed-policy fail-closed demand proved unsatisfiable during task 2.1: replaced by the trust model, owned configuration roots, host parent policy, and the administrator-policy and identity gates (see the resolution section).

Structural review: 5 requirement areas / 25 criteria, design within 300 lines, 11 leaf implementation tasks with boundary ownership and dependencies. The spec PRs contain no code.

## Managed-Policy Blocker Resolution (2026-10-11)
Source: task 2.1 blocker report ([#705 comment 6114925595](https://github.com/matdev83/go-llm-interactive-proxy/issues/705#issuecomment-6114925595)) and research response ([comment 6114964620](https://github.com/matdev83/go-llm-interactive-proxy/issues/705#issuecomment-6114964620)).

**Observed (implementer's isolated probes; real adapter 0.89.1, SDK 0.3.293, bundled CLI 2.1.293, SHA-256 `8968405e26db478af44eabc4635ab5ca557057b702a54460a59c13e1b253e978`; synthetic credentials only):** managed files and drop-ins executed credential helpers and SessionStart hooks in both auth modes; managed provider settings routed to Bedrock; a managed file created after `session/new` took effect later; a cached `remote-settings.json` executed hooks/helpers offline; `--bare` suppressed ordinary hooks but not provider routing or `policyHelper`.

**Source-derived:**
- Claude Code applies managed settings above every other level; no user, project, local or `--settings` value overrides them ([managed-settings](https://code.claude.com/docs/en/managed-settings)). Sources include `/etc/claude-code/managed-settings.json` and `managed-settings.d/`, MDM/HKLM, the user-writable HKCU fallback, `/etc/claude-code` on WSL (user-writable there), `policyHelper`, and server-managed settings cached at `remote-settings.json`.
- Server-managed settings exist only for Team/Enterprise organisations, are polled hourly, and in Agent SDK/non-interactive runs are applied for that run without the approval dialog ([server-managed-settings](https://code.claude.com/docs/en/server-managed-settings)). They are documented as a client-side control, not a security boundary.
- An embedding Agent SDK host may add restrictive policy through the SDK `managedSettings` option (parent settings); parent settings are ignored when an administrator source is present unless the administrator opts into merging.
- `claude setup-token` produces a one-year subscription OAuth token through the same browser flow as `/login`, saves it nowhere, and is documented for scripts and CI; `CLAUDE_CODE_OAUTH_TOKEN` ranks above `/login` and below API key and provider variables; `--bare` ignores it ([authentication](https://code.claude.com/docs/en/authentication)). `CLAUDE_CONFIG_DIR` scopes credentials, settings and session history (and the macOS keychain entry).
- Adapter `src/managed-policy.ts` deliberately copies the managed tier's `env` into the adapter process before any SDK call; with no administrator source it is a no-op. The adapter forwards `managedSettings`, `settingSources`, `settings`, `tools`, `plugins`, `strictMcpConfig` and `env` from `_meta.claudeCode.options`.

**Root cause:** requirements 2.2, 2.4 and 3.4 (as merged in #926) demanded that the connector neutralise or pre-reject administrator-tier policy as a security guarantee. That tier is designed to be unoverridable, executes code during evaluation, and changes during a session; every wrapper of the official CLI (this adapter, a project-owned SDK bridge, a fork) inherits it, and masking it would evade organisation policy. The observed effects are intended behaviour of that tier, not leaks through connector controls.

**Decisions adopted (owner-directed repair):**
- D1: administrator-tier policy is trusted out-of-band authority; never bypassed; root or same-user attackers are outside the `local_only` model.
- D2: V1 supports three credential sources: `api_key` (default), `subscription_token` (operator-run `claude setup-token`, secret, fresh owned root), and `host_login` (host configuration directory, disclosed as same trust as the operator's own CLI). Copying, linking or bind-mounting credential files is rejected (credential handling; refresh-token rotation would diverge copies).
- D3: `admin_policy: refuse` is the default; `honor` is an explicit opt-in with disclosure.
- D4: under `refuse`, a Team/Enterprise organisation credential is treated as organisation policy and rejected.
- D5: `api_key` and `subscription_token` run with a synthetic owned home and configuration root per process; `host_login` necessarily uses the host's.

**Alternatives rejected:** own TypeScript SDK bridge or adapter fork (same CLI and policy tier); Linux namespace/container masking of policy locations (evades organisation policy, Linux-only); `--bare` (does not stop `policyHelper` or provider routing and drops the subscription token); raw OAuth to the Messages API (impersonation).

**Unverified, owned by task 2.1:** each parent-settings key honoured as a parent setting on CLI 2.1.293; `auth status --json` field names for the API-key, token and host-login identities and organisation type; whether `auth status` executes anything without an administrator source (none expected); synthetic-home side effects; absence of server policy fetch for Pro/Max tokens in an empty root; WSL and Windows policy locations (documentation only). If a parent-settings key is not honoured, the design requires another honoured control to exclude the same effect before the profile is enabled.
